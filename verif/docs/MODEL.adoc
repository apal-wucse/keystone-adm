博士論文第3章「Efficient Large-Scale Data Transfer Approach over the Trust Boundary」の設計を、状態遷移系として定式化したもの。特定の検証ツールには依存しない。TLA+ などへの機械可読な記述は、本書を仕様の原本として別途作成する。

* 1〜7節は**論文どおりの設計モデル**を記述する。
* 実装（`++sm/src/++`）がこのモデルと食い違う箇所は8節にまとめる。8節はコード読解で見つけた候補で、そのうち6項目の影響を10.3節の実装モデルで検査した。実機での確認はしていない。

英語版：`MODEL.en.adoc`（PDF は `MODEL.en.pdf`）。内容は同一で、節番号と ID も共通。

記法：`++x'++` は遷移後の値、`++∀h++` は全 hart、`++⊥++` は未定義、`++[a, b)++` は半開区間。

== 1. 範囲と前提

=== 1.1 対象

* Security Monitor (SM) による ADM の保護と検証。
* 構成は `++DEFAULT_NOPERM++`（ADM は既定でホストからアクセス不可）に固定。
* エンクレーブは単一スレッド（`++MAX_ENCL_THREADS = 1++`）。

=== 1.2 対象外

* `++DEFAULT_READ++` モード。
* ランタイム（RT）と eapp の内部。両者は「任意の共有状態・任意のメタデータで stop を呼びうる主体」として抽象化する。
* DoS、物理攻撃、サイドチャネル（論文3.3節）。
* アテステーション、private memory（EPM）の保護そのもの（元の Keystone の性質として仮定）。

=== 1.3 敵対者（論文3.3節）
敵対者は次を行える。

* ホスト文脈にある全 hart の制御。PMP が許す範囲での任意のメモリ読み書き。
* ホスト用 SBI（create / run / resume / destroy）の任意の順序・引数・hart からの発行。
* 悪意あるエンクレーブの起動。そのエンクレーブは任意の引数でエンクレーブ用 SBI（stop 系 / exit）を発行する。

=== 1.4 仮定（モデルの外で成立を前提とするもの）
[cols="2,10",options="header"]
|===
| ID
| 仮定

| H1
| PMP はRISC-V 特権仕様どおりに動作する。S/U モードのアクセスは、マッチする最小番号のエントリの権限に従う

| H2
| SM のコードとデータは S/U モードから読み書きできない（最優先 PMP エントリ）

| H3
| 全 hart への PMP 更新（IPI）は同期的である。更新要求は、対象の全 hart が適用を終えるまで戻らない

| H4
| 全 hart が IPI の対象である。停止中で後から起動する hart も、起動時に正しい PMP 設定を得る

| H5
| SM 自身（M モード）の ADM アクセスは PMP に妨げられない

| H6
| PMP を経由しないメモリアクセス経路（DMA など）は存在しない

| H7
| エンクレーブ用 SBI の発行元エンクレーブは、SM が hart ごとに保持する文脈情報から正しく特定される

|===

H3・H4 は検証事項 D4 と表裏であり、設計モデルでは仮定、実装検証では証明対象とする。

== 4. 初期状態

....
∀e: state[e] = INVALID, share[e] = NONE, meta[e] = ∅, phase[e] = IDLE,
    runner[e] = ⊥, epm[e] = utm[e] = adm[e] = ⊥,
    dirty[e] = FALSE, dead[e] = FALSE
∀h: ctx[h] = HOST
∀h, e: pmp[h][e] = NONE
observed = ∅
....

== 5. 遷移

各遷移は「ガードが成立するとき、効果が原子的に起きる」ものとする。書かれていない変数は変化しない。

=== 5.1 SM の操作

==== Create(h, e, R_epm, R_utm, R_adm, m0) — ホストが発行
[cols="1,6"]
|===
| ガード
| `++ctx[h] = HOST++`、`++state[e] = INVALID++`、`++NoOverlap(R_epm, R_adm)++`（7.3節 C1）、PMP エントリに空きがある、`++\|dom(m0)\| ≤ SLOT_MAX++`

| 効果
| `++epm[e]' = R_epm++`、`++utm[e]' = R_utm++`、`++adm[e]' = R_adm++`、`++∀h': pmp[h'][e]' = NONE++`、`++share[e]' = RW++`、`++meta[e]' = m0++`、`++state[e]' = FRESH++`、`++dirty[e]' = TRUE++`、`++sentMeta[e]' = m0++`、`++dead[e]' = FALSE++`

|===

* `++share = RW++` は「ホストが ADM を初期化済みで、初回実行前に検証が必要」を表す。
* `++m0++` はホスト（敵対者）が与える。初期検証は「ADM が `++m0++` と整合する」ことだけを保証する。初期状態（`++m0++` と初期内容）が正しいかどうかは、エンクレーブが正しく起動したかをアテステーションで判断する範疇であり、本モデルの範囲外とする（論文3.6.4節）。
* ガードが不成立なら何も変化しない（C5）。

==== RunBegin(h, e) — ホストが発行
[cols="1,6"]
|===
| ガード
| `++ctx[h] = HOST++`、`++state[e] = FRESH++`

| 効果
| `++state[e]' = RUNNING++`、`++ctx[h]' = SM(e)++`、`++runner[e]' = h++`、`++phase[e]' = VALIDATING++`

|===

create 時点で全 hart の権限が NONE なので、回収段階を経ずに検証へ進む。

==== ResumeBegin(h, e) — ホストが発行
[cols="1,6"]
|===
| ガード
| `++ctx[h] = HOST++`、`++state[e] = STOPPED++`、`++phase[e] = IDLE++`

| 効果
| `++state[e]' = RUNNING++`、`++ctx[h]' = SM(e)++`、`++runner[e]' = h++`、`++phase[e]' = REVOKING++`

|===

==== RevokeStep(h', e) — SM 内部（IPI による各 hart での適用）
[cols="1,6"]
|===
| ガード
| `++phase[e] = REVOKING++`、`++pmp[h'][e] ≠ NONE++`

| 効果
| `++pmp[h'][e]' = NONE++`

|===

==== RevokeDone(e) — SM 内部
[cols="1,6"]
|===
| ガード
| `++phase[e] = REVOKING++`、`++∀h': pmp[h'][e] = NONE++`

| 効果
| `++phase[e]' = VALIDATING++`

|===

回収を hart ごとの段階に分けているのは、IPI 同期の途中状態（一部の hart だけ権限が残っている状態）で検証やエンクレーブ再開が始まらないことを性質として述べるため。

==== ValidatePass(e) — SM 内部
[cols="1,6"]
|===
| ガード
| `++phase[e] = VALIDATING++`、かつ `++share[e] ≠ RW++` または `++WF(mem[e], \|adm[e]\|, meta[e])++`（6節）

| 効果
| `++share[e]' = NONE++`、`++meta[e]' = ∅++`、`++share[e] = RW++` だった（内容を検査した）場合に限り `++dirty[e]' = FALSE++`、続けて Enter

|===

**Enter**（ValidatePass の効果の一部）：`++h = runner[e]++` として `++pmp[h][e]' = RW++`、`++ctx[h]' = ENC(e)++`、`++phase[e]' = IDLE++`。

==== ValidateFail(e) — SM 内部
[cols="1,6"]
|===
| ガード
| `++phase[e] = VALIDATING++`、`++share[e] = RW++`、`++¬WF(mem[e], \|adm[e]\|, meta[e])++`

| 効果
| `++dead[e]' = TRUE++`、`++ctx[runner[e]]' = HOST++`、`++runner[e]' = ⊥++`、`++phase[e]' = IDLE++`、続けて DestroyBody(e)

|===

論文3.6.4節「SM は即座にエンクレーブを破棄する」に対応する。

==== StopShare(h, e, s, m) — 所有エンクレーブが発行（エッジコール）
[cols="1,6"]
|===
| ガード
| `++ctx[h] = ENC(e)++`、`++state[e] = RUNNING++`、`++s ∈ Share++`、`++s = RW ⇒ m ≠ ⊥ ∧ \|dom(m)\| ≤ SLOT_MAX++`

| 効果（共通）
| `++state[e]' = STOPPED++`、`++share[e]' = s++`、`++ctx[h]' = HOST++`、`++runner[e]' = ⊥++`、`++snap[e]' = mem[e]++`、`++lastShare[e]' = s++`

| 効果（`++s = NONE++`）
| `++pmp[h][e]' = NONE++`、`++meta[e]' = ∅++`

| 効果（`++s = RONLY++`）
| `++∀h': pmp[h'][e]' = R++`、`++meta[e]' = ∅++`

| 効果（`++s = RW++`）
| `++∀h': pmp[h'][e]' = RW++`、`++meta[e]' = m++`、`++sentMeta[e]' = m++`、`++dirty[e]' = TRUE++`

|===

* ガード不成立の呼び出し（値域外の `++s++`、`++RW++` でメタデータなし）は拒否され、状態は変化しない。
* 権限付与は原子的とする。付与の途中状態では呼び出し hart は SM 内にあり、エンクレーブは実行されていないため、段階に分けても性質に影響しない。
* 付与は全 hart が対象であり、他エンクレーブを実行中の hart も含む。共有は非信頼側への公開だからである（A6 は非共有時のみの性質）。

==== StopInvoluntary(h, e) — タイマ割込みなど、共有指定のない停止
[cols="1,6"]
|===
| ガード
| `++ctx[h] = ENC(e)++`、`++state[e] = RUNNING++`

| 効果
| StopShare(h, e, NONE, ⊥) と同じ

|===

==== Exit(h, e) — 所有エンクレーブが発行
[cols="1,6"]
|===
| ガード
| `++ctx[h] = ENC(e)++`、`++state[e] = RUNNING++`

| 効果
| StopShare(h, e, NONE, ⊥) と同じ

|===

==== Destroy(h, e) — ホストが発行
[cols="1,6"]
|===
| ガード
| `++ctx[h] = HOST++`、`++state[e] ∈ {FRESH, STOPPED}++`、`++phase[e] = IDLE++`

| 効果
| `++state[e]' = DESTROYING++`、続けて DestroyBody(e)

|===

**DestroyBody(e)**（この順序で実行）：

. `++mem[e]' = 0++`（ADM と EPM をゼロ化）
. `++∀h': pmp[h'][e]++` のエントリを解放。`++adm[e]' = epm[e]' = utm[e]' = ⊥++`（以後この物理領域はホストのもの）
. `++share[e]' = NONE++`、`++meta[e]' = ∅++`、`++state[e]' = INVALID++`

=== 5.2 所有エンクレーブの操作
[cols="3,6,3",options="header"]
|===
| 遷移
| ガード
| 効果

| EncRead(h, e)
| `++ctx[h] = ENC(e)++`、`++pmp[h][e] ∈ {R, RW}++`
| エンクレーブが `++mem[e]++` を読む

| EncWrite(h, e, v)
| `++ctx[h] = ENC(e)++`、`++pmp[h][e] = RW++`

=== 5.3 敵対者の操作
`++ctx[h] = HOST++`、または `++ctx[h] = ENC(e2)++` で `++e2 ≠ e++` のとき、h は e に対して敵対的とみなす。

[cols="3,6,10",options="header"]
|===
| 遷移
| ガード
| 効果

| AdvRead(h, e)
| h は e に対して敵対的、`++pmp[h][e] ∈ {R, RW}++`
| `++observed' = observed ∪ {(e, mem[e])}++`

| AdvWrite(h, e, v)
| h は e に対して敵対的、`++pmp[h][e] = RW++`
| `++mem[e]' = v++`（任意の値）、`++dirty[e]' = TRUE++`、`++secret[e]' = FALSE++`

| ホスト用 SBI
| `++ctx[h] = HOST++`
| 5.1節の Create / RunBegin / ResumeBegin / Destroy を任意の引数で試行

| 悪意エンクレーブ
| `++ctx[h] = ENC(e2)++`
| e2 について StopShare / Exit を任意の引数で試行

|===

== 6. 検証関数の仕様

=== 6.1 ADM のデータ構造（論文3.6.3節）
ADM 先頭からのオフセットで位置を表す。`++S++` を ADM のサイズとする。

....
ADM ヘッダ（オフセット 0、大きさ HDR）
  n            : 有効なデータ領域の数
  hoff[0..15]  : 各領域ヘッダへのオフセット
  uid[0..15]   : 各領域の UID

領域ヘッダ（オフセット hoff[i]、大きさ RHDR）
  type         : 領域の型
  doff         : データ本体へのオフセット
  dsize        : データ本体の大きさ（バイト）
....

領域 i について `++H_i = [hoff[i], hoff[i] + RHDR)++`（ヘッダ）、`++D_i = [doff_i, doff_i + dsize_i)++`（データ本体）と書く。算術はすべて数学的整数で行う（桁あふれによる回り込みを許さない）。

=== 6.2 構造述語 WF(mem, S, meta)
次のすべてが成り立つこと。

[cols="2,11",options="header"]
|===
| ID
| 条件

| W1
| `++n ≤ SLOT_MAX++`

| W2
| `++uid[0..n-1]++` は互いに異なり、いずれも非零で、集合として `++dom(meta)++` に等しい（領域数と識別子の一致）

| W3
| `++∀i < n++`: `++HDR ≤ hoff[i]++` かつ `++hoff[i] + RHDR ≤ S++`

| W4
| `++∀i < n++`: `++doff_i + dsize_i ≤ S++`

| W5
| `++hoff[0] < hoff[1] < … < hoff[n-1]++`

| W6
| ADM ヘッダ `++[0, HDR)++`、すべての `++H_i++`、すべての `++D_i++` は互いに重ならない

| W7
| `++∀i < n++`: `++type_i = meta[uid[i]].type++`

| W8
| `++∀i < n++`: `++doff_i = meta[uid[i]].offset++`

| W9
| `++∀i < n++`: `++SizeOK(type_i, dsize_i, meta[uid[i]].size)++`

|===

`++SizeOK(t, d, s)++`：
[cols="5,3",options="header"]
|===
| 型
| 条件

| BYTE / I16 / I32 / I64
| `++d = 1 / 2 / 4 / 8++`

| STATIC_ARR_w（w = 1, 2, 4, 8）
| `++d = s × w++`

| ARR_w（可変長配列）
| 制約なし（W4・W6 の範囲検査のみ）

| DYN_ALLOC
| `++d = s++`

|===

可変長配列は、エンクレーブがデータの大きさを問わないときに選ぶ型であり、`++dsize++` を期待値と照合しないのは意図された設計である。この型では「数・型・オフセット」と範囲（W4・W6）だけが検証される。

=== 6.3 検証関数に対する要求

* **健全性（B6）**：検証関数が成功を返す ⇒ `++WF(mem, S, meta)++`。
* **安全性（B7）**：任意の `++mem++`、任意の `++meta++`、任意の `++S > 0++` に対し、検証関数は `++[0, S)++` の外を読まず、何も書かず、桁あふれを起こさず、停止する。

== 7. 性質

=== 7.1 A. アクセス制御（R1）

[cols="2,5,12,2",options="header"]
|===
| ID
| 主張
| 形式的な記述
| 論文

| A1
| 作成直後、どの hart も ADM にアクセスできない
| `++state[e] = FRESH ⇒ ∀h: pmp[h][e] = NONE++`
| 3.6.2

| A2
| 実行中、ADM にアクセスできるのは実行 hart だけ
| `++ctx[h] = ENC(e) ⇒ pmp[h][e] = RW ∧ ∀h2 ≠ h: pmp[h2][e] = NONE++`
| 3.6.2, 3.8.1

| A3
| 所有者以外の権限は、エンクレーブが明示した共有状態を超えない
| `++ctx[h] ≠ ENC(e) ∧ adm[e] ≠ ⊥ ⇒ pmp[h][e] ≤ hostPerm(share[e])++`
| 3.5.2, 3.8.1

| A4
| ホストは権限を保持したままエンクレーブを再開できない
| Enter は `++∀h: pmp[h][e] = NONE++` のときにだけ起きる
| 3.6.5, 3.8.1

| A5
| ADM に実行権限は付かない
| どの hart の ADM 用 PMP エントリも常に X = 0
| 3.9.3

| A6
| 非共有時、他エンクレーブは ADM にアクセスできない

C1 の帰結として、次の2つを検査する。どちらも、あるアドレスにマッチするエンクレーブ用エントリすべての権限を対象に述べるので、エントリ間の優先度の順序によらず成り立つ。

* **private memory の隔離**：e の private memory の各ページについて、e を実行していない hart では、マッチするエントリが e の EPM エントリ（権限なし）だけである。ADM の共有が他エンクレーブの private memory を露出することはない。
* **ADM 権限の忠実性**：e の ADM の各ページについて、マッチするエントリの権限がちょうど `++pmp[h][e]++` である。これにより、A・B の性質は抽象的な `++pmp[h][e]++` から物理アドレスに持ち上がる。

* **変異試験**：回収段階の省略（A2 が破れる）、全 hart の回収を待たない（B2）、内容を検査しない（B5）、他エンクレーブとの重なり検査の省略（C1 と private memory の隔離）で、それぞれ違反が検出される。

=== 10.2 Rocq による設計モデルの証明

証明は `++verif/rocq/++` にある。`++make prove++` で全証明を検査し、どの定理も公理に依存しないこと（`++Print Assumptions++` がすべて "Closed under the global context" を返すこと）を確認する。

TLA+ との違いは保証の範囲である。hart、エンクレーブ、ADM の内容、メタデータを任意の型とし（hart とエンクレーブ ID は等号が決定可能であることだけを仮定する）、構造述語 WF も任意の述語のまま扱う。TLA+ では WF(d, m) を d = m に固定していた。したがって以下の結果は構成の大きさによらない。

方法は次のとおり。`++ADM.tla++` の遷移を帰納的な遷移関係 `++step++` として書き写し、帰納的不変条件 `++Inv++` を定めて、初期状態で成り立ち各遷移で保たれることを示す。7節の性質は `++Inv++` から導く。遷移の性質（A4、A7、A9、B5 の遷移形、D1）は、到達可能な状態からの1ステップについての定理として述べる。

* **不変条件の補強**：7節の性質だけでは帰納的にならない。主に次を加えている。

** RUNNING 以外では phase は IDLE か、破棄中の ZEROED である。
** ゼロ化した後は `++secret++` が偽である（A9 に必要）。
** `++dirty++` なら share = RW である（B1 に必要）。
** 最後の停止が RW 共有でなければ share ≠ RW である（E2 に必要）。
* **TLA+ との対応**：`++ValidatePass++` と `++ValidateFail++` は、ガードで runner を名指す（`++runner s e = Some h++`）。到達可能な状態では TLA+ の `++runner[e]++` と一致する。
* **領域付きモデルの網羅性**：`++ADMRegions.v++` の `++step_cases++` で、設計モデルの遷移が Create、DestroyFree、エンクレーブの存在を変えない遷移のいずれかであることを示した。したがって領域付きモデルの遷移は、設計モデルのすべての遷移を覆う。
* **空虚でないこと**：同じモデルに対する TLA+ の到達可能性確認（10.1節）で担保する。
* **検査時間**：`++ADM.v++` は4〜5分、最大メモリ約 3.5 GB かかる。汎用の自動証明タクティクで、全遷移と不変条件の全節の組を場合分けしているためである。

=== 10.3 実装モデルの検査

仕様は `++verif/tla/ADMImpl.tla++` にある。設計モデル（`++ADM.tla++` など）とは独立したモジュールで、設計モデルには手を加えていない。`++sm/src/++` の `++enclave.c++`、`++adm.c++`、`++ipi.c++`、`++pmp.c++`、`++sm.c++` と OpenSBI 1.1 に従い、ロックを外す箇所や hart をまたぐ箇所で遷移を分割している。

モデル化の要点は次のとおり。

* **PMP**：hart ごとの ADM エントリ（NONE / R / RW / 未設定）で表す。未設定のエントリは最低優先度の OS 領域に落ち、ホスト文脈では全権限、エンクレーブ文脈では権限なしになる。性質はこの実効権限で述べる。
* **IPI と HSM**：`++pmp_set_global++` が届くのは interruptible な hart だけである。HSM の hart_stop / hart_start / hart_suspend をモデルに含め、設計モデルで仮定としていた D4 を外した。HSM の状態は、OpenSBI 1.1 の warm boot と復帰の手順に合わせて細分化した（START_PENDING を `++sm_init(false)++` の前後で分け、STARTED になってから S モードへ移るまでを別の状態とする）。STARTED でない hart と、SM の処理中（M モード）の hart は、ADM への実効権限を持たないものとする。
* **停止**：3種類の停止は、ロック内で状態を変える遷移と、ロックの外で `++context_switch_to_host++` を行う遷移（`++StopSwitch++`）に分けた。後者は、その時点の `++share++` を読む。
* **性質**：7節の性質を、同じ名前・同じ意味のまま実効権限に読み替えた。B3 は、設計どおりの形（破棄される）と弱い形（二度と実行されない）の両方を検査する。
* **修正フラグ**：8節の差分ごとに `++Fix*++` 定数を設けた。すべて偽が修正前の実装、すべて真が修正版である。#7 は2つのフラグに分かれ、修正の方式を `++RestoreAt++` で選ぶ（次項）。

==== 主な反例

. **HSM による hart の再起動（#7）**：ホストが hart を hart_stop してから hart_start すると、その hart には SM 領域と OS 領域しか設定されない。その hart のホストは、OS 領域を通じて全メモリに全権限を持つ。エンクレーブが別の hart で実行中でも ADM を読み書きでき、A2 と E1 が破れる（EPM も同様と考えられる）。ホストだけで成立し、エンクレーブ側の協力は要らない。元の Keystone に由来する。非保持型サスペンドからの復帰でも同じことが起きる。
+
再起動した hart に `++sm_init(false)++` で設定し直すだけでは足りない（`++RestoreAt = init++`）。その hart は START_PENDING のまま設定を終え、STARTED になるまでの間に他の hart が行った `++pmp_set_global++` を受け取らない。たとえば、エンクレーブの create 直後や resume による回収の直後に、その hart だけが古い権限を持ったまま STARTED になる。
. **停止と再開の競合（#13、新規）**：停止した hart がロックを外してから `++context_switch_to_host++` を終えるまでの間に、別の hart から次のことができる。
** resume する。resume の回収（`++pmp_set_global(NO_PERM)++`）が先に終わり、その後で停止側が RW 共有を全 hart に付与する。エンクレーブは再開しているのに、ホストの hart が RW を持つ（E1、B2）。
** destroy してから同じ ID で create する。遅れた `++context_switch_to_host++` は新しいエンクレーブの `++share++`（create 直後は RW）を読み、その ADM に全 hart で RW を付与する（A1）。共有を指定しない exit や割込みによる停止でも起きる。
+
ホストは停止の直後に resume や destroy を発行するだけでよい。モデル化していないが、`++threads[0]++` のレジスタ文脈の入れ替えも、resume 側の入れ替えと競合する。
. **NULL メタデータでの RW 共有（#12、新規）**：`++stop_enclave_with_share++` がこの呼び出しを拒否するのは、状態を STOPPED（`++n_thread = 0++`）にした後である。エンクレーブはエラーを受け取って実行を続ける。ホストは別の hart から次のことができる。
** resume して、同じエンクレーブを2つの hart で実行させる（D2d、A2）。
** 実行中のエンクレーブを destroy する。ゼロ化の後にエンクレーブが書いた内容が、領域の解放とともにホストへ渡る（A9、E1）。
+
ランタイムの `++dispatch_edgecall_ocall_with_share++` は eapp が渡した引数をそのまま SM に渡すので、eapp の呼び出し方ひとつでこの経路に入る。
. **二重 destroy（#11）**：DESTROYING も destroy のガードを通るため、同じ ID への destroy が2つの hart で並行に進みうる。遅れた側が、先に完了した破棄の後に同じ ID で作られた新しいエンクレーブの ADM をゼロ化し、エントリを解除する。新しいエンクレーブの実行中に、その ADM がホストへ露出する（A2、E1）。ホストだけで成立するが、遅れた側の破棄処理と、新しいエンクレーブの作成・実行が交錯するタイミングを要する。元の Keystone に由来する。
. **メタデータの残留（#5）**：NONE または RONLY 共有の停止で渡したメタデータが残り、後の RW 共有の検証に使われる。エンクレーブが今回渡していない UID の領域をホストが置いても、検証を通る（B4、B5）。
. **検証失敗（#1）**：エンクレーブは破棄されず、RUNNING・`++n_thread = 1++` のまま残る。実行もされないので、B3 の弱い形は成り立つ。ゼロ化と PMP エントリの解放が行われない、資源の問題にとどまる。
. **`++share_type++`（#6）**：単独では、どの性質も破らない。

==== 注意

* 反例はモデル上のものである。QEMU や実機での再現は行っていない。OpenSBI の挙動は、ビルドに使う 1.1 のソースの読解に基づく。
* EPM、UTM、create の途中状態（ALLOCATED）はモデル化していない。
* `++pmp_set_global++` の IPI の1往復と、`++init_resend++` の送り直しは、1つの原子的な遷移として扱う。記録と HSM の状態の間のメモリ順序（`++mb()++` の位置）はモデルの外の仮定である。
* 修正フラグは修正方針の一案をモデル化したもので、実装を修正したものではない。モデル化した差分（#1, #5, #6, #7, #11, #12, #13）は、いずれも実装も修正済みである。

* B7：`++data->offset + data->size++` の桁あふれ（#4）、`++meta.size++` × 要素幅の桁あふれ。S が ADM ヘッダより小さいと範囲外を読むが、ADM はページ単位なので実際には起きない。
* B6：W2（UID の重複、期待する領域の欠落。#2）、W3（領域ヘッダが ADM ヘッダと重なる）、W4（桁あふれ。#4）、W6（ヘッダ同士・ヘッダとデータ・データ同士の重なり。#4）、W7（型を照合しない。#3）、W9（掛け算の桁あふれ）。W1、W5、W8 は成り立っていた。

最も危険なのは W4 である。可変長配列型の領域に巨大な `++size++` を書けば、`++offset + size++` が回り込んで検証を通る。その `++size++` を信じたエンクレーブは ADM の外を読み書きする。

修正（`++adm.c++`）：

* 領域数をメタデータの使用中エントリ数と照合し、UID の重複と未知の UID を拒否する（W2）。
* 領域ヘッダは ADM ヘッダの後ろ・ADM の中にあり、直前のヘッダと重ならないこと（W3、W5、W6）。
* データ本体の範囲を `++size > S || offset > S - size++` の形で検査し（W4）、ADM ヘッダ・すべての領域ヘッダ・他のデータ本体と重ならないこと（W6）。
* 領域ヘッダの型をメタデータと照合する（W7）。大きさは割り算で照合する（W9）。
* ADM の各フィールドを一度だけ読む。
* 新しいエラーコード `++ADM_REGION_COUNT_MISMATCH++`、`++ADM_INVALID_UID++`、`++ADM_TYPE_MISMATCH++` を追加した。

SDK とランタイムが作る ADM は、修正後の検査も通る。ランタイムは stop のたびにすべての領域をメタデータとして渡し、型も領域ヘッダに書いている。修正後の SM とドライバで作ったイメージで、`++hello-adm.ke++` が動作することも確認した。

保証の範囲：B6 は領域数6以下での結果である（領域数6で約86分）。各条件は高々2つの領域の関係なので、上限を上げても新しい種類の違反は生じないと考えられるが、証明はしていない。領域数16のままでは、記号的な位置からの読み出しが多く、検査が終わらなかった。B7 は領域数16まで含む（検査に約20分）。

==== PMP 領域の割当（C2、C3、C5）

`++pmp_regions.c++` は `++sm/src/pmp.c++` をそのまま取り込み、PMP の CSR を配列に置き換えて検査する（OpenSBI のヘッダは、SM のビルドに使うパッチ済みのものを使う）。`++sm_init++` と同じく SM 領域と OS 領域を作った後、任意の K 回の操作（`++PMP_PRI_ANY++` または `++PMP_PRI_BOTTOM++` での割り当て、解放）を行い、`++PMP_PRI_ANY++` / `++PMP_PRI_TOP++` で作った任意の領域について次を確かめる。物理アドレスは56ビット、pmpaddr は54ビットとする。

* C2：エントリは SM のエントリより後、OS のエントリより前にある。
* C3：他の領域とエントリを共有しない。その領域だけを書き込んだとき、エントリがマッチするアドレスの集合はちょうど `++[addr, addr + size)++` である（RISC-V の TOR / NAPOT のマッチ規則で計算する）。
* C5：割り当てが失敗したとき、`++reg_bitmap++` と `++region_def_bitmap++` は変わらない。

修正前の実装では、C2 と C3（エントリの共有）に反例があった（8節 #14）。反例は、UTM を割り当てて解放した後に TOR の領域を3つ割り当て（レジスタ1〜6）、さらに NAPOT の領域を割り当てるとレジスタ7（OS と共有）を受け取る、というものである。`++PMP_PRI_ANY++` の空き探索から最下位のレジスタを除いて修正した後は、K = 6（約15分）と K = 8（約65分）で全項目が成り立つ。TOR・NAPOT 両方の領域に到達することも確かめた。C3 の符号化（TOR の下限レジスタ、NAPOT のマスク）と C5 は、修正前から成り立っていた。

`++create_enclave++` の失敗時の後始末（C5 のエンクレーブ側）は、コード読解で確認した。割り当てた領域を逆順に解放し、設定した全 hart のエントリを解除してから eid を返す。

=== 10.5 QEMU での確認

`++verif/qemu/run-tests.sh [BIOS]++` は、`++run-virt++` のイメージを新しいオーバーレイで起動し（`++BIOS++` を与えると SM をそれに差し替える）、テストアプリ `++admfail.ke++` と `++admpeek.ke++` を送り込んで実行する。

* `++admpeek++`（#7）：エンクレーブを作った後、CPU ホットプラグで CPU を停止・再起動し、その CPU からホストの ADM のマッピングを読む。
